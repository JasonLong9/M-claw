# Mclaw 技术架构草案

## 1. 架构目标

Mclaw 的技术架构目标不是重写现有 Qclaw，而是在现有 Electron + OpenClaw 管理能力之上，补齐产品化交付所需的四层能力：

1. 可交付安装层。
2. 稳定运行与自动恢复层。
3. 官方渠道接入层。
4. 安全与商业化预埋层。

## 2. 现有能力基线

根据当前仓库结构，已可确认已有以下能力基础：

| 能力 | 现状 |
|---|---|
| Electron 桌面壳 | 已有 |
| React 前端页面与向导流程 | 已有 |
| OpenClaw 配置与运行时接管 | 已有 |
| gateway health / restart / ensure running | 已有 |
| 飞书官方插件状态、安装与修复 | 已有 |
| 备份、恢复、升级、清理 | 已有 |
| preload 隔离与 IPC 分层 | 已有 |
| 大量单测 | 已有 |

Mclaw 不应推翻上述基线，而应在其上做受控扩展。

## 2.1 当前平台状态判断

结合仓库现状，可以得出以下工程判断：

1. Windows 已有部分实现，不属于从零起步。
2. 但当前仓库的发布链路、验收链路和部分文案仍明显偏向 macOS。
3. 因此架构演进的重点不是“再设计一个新平台层”，而是先把已有的 Windows 分支收口成可交付形态。

当前已确认的事实：

1. 已存在 Windows 打包配置。
2. 已存在 `win32` 运行分支、PATH 刷新、`powershell` / `msiexec` 安装逻辑。
3. 已存在 Windows 自动更新支持声明。
4. 但正式发布脚本、预检脚本、README 平台状态仍未对齐到“Windows 已就绪”。

## 3. 目标架构分层

```text
┌──────────────────────────────────────────────┐

├──────────────────────────────────────────────┤

├──────────────────────────────────────────────┤
│ Desktop Service 层                           │
│ 看门狗控制器、安装编排、接入编排、脱敏策略      │
│ 平台兼容编排、发布收口                        │
├──────────────────────────────────────────────┤
│ OpenClaw Runtime Adapter 层                  │

├──────────────────────────────────────────────┤

└──────────────────────────────────────────────┘
```

## 4. 模块划分

### 4.1 桌面 UI 层

职责：

1. 承载首次启动向导。
2. 提供飞书接入按钮式体验。
3. 展示 gateway 状态、最近恢复结果、日志摘要。
4. 为后续授权状态、试用状态预留页面入口。

约束：

1. UI 不直接读写敏感文件。
2. UI 不直接持有系统级执行权限。
3. 所有高风险动作必须经主进程受控 IPC。

### 4.2 Desktop Service 层

建议新增或强化的核心服务：

| 服务 | 作用 |
|---|---|
| `watchdog-service` | 定时健康检查、自动恢复、熔断、事件记录 |
| `first-run-orchestrator` | 首次启动流程编排 |
| `channel-onboarding-service` | 飞书接入、状态同步、修复闭环 |
| `redaction-policy-service` | 输出脱敏与日志脱敏 |
| `installation-identity-service` | 安装身份生成与本地持久化 |
| `desktop-platform-adapter` | 统一 Windows/macOS 路径、命令、文案和平台差异行为 |

### 4.3 OpenClaw Runtime Adapter 层

复用现有模块能力，并统一形成 Mclaw 自己的“适配层”，避免 UI 和上游细节直接耦合。

建议适配对象：

1. gateway 健康检查与重启能力。
2. OpenClaw 配置写入与补丁应用能力。
3. 官方插件安装、修复与状态查询能力。
4. 备份、恢复、升级与清理能力。

### 4.4 本地状态与安全层

职责：

1. 保存安装身份与版本状态。
2. 保存脱敏日志索引。
3. 定义允许插件、允许技能、允许执行动作的策略。
4. 保存授权状态占位信息。

### 4.5 平台兼容适配层

该层不是替代 `OpenClaw Runtime Adapter`，而是约束“平台差异如何被产品化吸收”。

职责：

1. 统一 Windows/macOS 下的路径解析、目录命名、日志与备份目录策略。
2. 统一命令探测、提权、安装、PATH 刷新、进程拉起与 shell 语义。
3. 统一首次启动、错误提示、修复文案中的平台差异。
4. 把平台差异限制在主进程与适配层，而不是散落在多个 UI 页面。

## 5. 核心技术路线

### 5.1 打包交付路线

现阶段建议采用“双轨决策”：

1. v1 主线先以当前 Electron 打包能力为基础，确保桌面产物稳定，并纳入 OpenClaw 内置交付。
2. Docker 作为专题预研，不直接阻塞 v1 主线。

原因：

1. 当前仓库已经具备 Electron Builder 产物链路。
2. 当前仓库已经具备一部分 Windows 运行逻辑，但发布链路和验收链路尚未完整。
3. Docker 在 Windows/macOS 上的实际安装体验、资源占用、系统权限和售后复杂度都更高。
4. `dev_guide.md` 里虽然把 Docker + 可执行程序列为明确方向，但从工程风险看，应先通过专题验证后再进入主线交付。

补充决策：

1. v1 当前阶段先做 `Windows 原生桌面收口 + OpenClaw 内置交付`，而不是 Docker 化收口。
2. 原因不是否定 Docker，而是原生桌面仍是当前最短交付路径。

### 5.1.1 OpenClaw 真内置本体交付策略

补充双平台约束：

1. runtime bundle 目录命名必须同时覆盖 Windows / macOS，而不是先写成单一 Windows 目录。
2. 当前建议固定以下结构：
   - `resources/openclaw-bundle/runtime/windows-x64/`
   - `resources/openclaw-bundle/runtime/darwin-arm64/`
   - `resources/openclaw-bundle/runtime/darwin-x64/`
3. manifest 必须能表达：
   - 当前默认交付模式
   - 最终目标交付模式
   - 当前平台/架构是否声明了 runtime artifact
   - 当前平台/架构的 runtime artifact 在打包产物中是否真实存在
4. 发现、安装、诊断链路都不得只输出 Windows 专属语义，必须可复用于 macOS。

目标：

1. 把 OpenClaw 从“首次启动安装依赖”改为“安装包随附可运行本体”。
2. 保证断网条件下首次启动仍可完成运行底座准备。

建议实现：

1. 打包阶段注入 `openclaw-bundle` 到应用资源目录（按平台区分可运行本体）。
2. 首次启动由 `first-run-orchestrator` 先执行本体验证、注册与可执行探测，再执行环境检测。
3. `tgz` 或在线 npm 安装仅作为 fallback，并在诊断信息中标记来源（`bundled-runtime` / `bundled-fallback` / `online-fallback` / `external`）。
4. 本体元数据（版本、hash、构建来源）纳入可观测状态，便于售后排查。
5. 当前 `v11` 的 `tgz` 方案只能视为过渡态，不能作为该策略的完成定义。

### 5.2 看门狗路线

建议采用分层看门狗，而不是单一“循环重启脚本”：

1. L1 健康感知：定时调用 health 与关键状态探针。
2. L2 自愈动作：尝试 `ensure running`、轻量重启、强制重启。
3. L3 熔断保护：连续失败达到阈值后停止自动重启，转人工诊断。
4. L4 可观测性：记录最后健康时间、最近错误、恢复次数、熔断原因。

### 5.3 飞书接入路线

建议维持“官方插件优先 + UI 编排层封装”：

1. 插件准备。
2. 安装会话或二维码获取。
3. 如接入 `larksuite/cli`，优先把它放在 OAuth / scope 授权适配层，而不是直接替换当前 `openclaw-lark` 插件安装层。
3. 用户扫码。
4. 回写状态。
5. 验证 gateway 与机器人可用性。

### 5.4 商业化预埋路线

v1 不接支付逻辑，但应定义统一数据结构：

```ts
type InstallationIdentity = {
  installationId: string
  deviceFingerprint?: string
  channelSource?: string
  inviteCode?: string
  entitlementStatus: 'unknown' | 'trial' | 'active' | 'expired'
  entitlementPlan?: string
  createdAt: string
  updatedAt: string
}
```

## 6. 数据与状态

### 6.1 推荐新增状态域

| 状态域 | 说明 |
|---|---|
| `watchdog` | 当前看门狗状态、最近检查时间、连续失败次数 |
| `installationIdentity` | 安装身份和商业化占位信息 |
| `securityPolicy` | 插件白名单、技能白名单、脱敏策略版本 |
| `channelOnboarding` | 飞书接入阶段与最近结果 |

### 6.2 日志分层

建议至少拆为三类日志：

1. 用户可见日志。
2. 技术诊断日志。
3. 安全事件日志。

其中用户可见日志必须脱敏。

## 7. 安全设计原则

1. `preload` 是唯一受信桥接层，Renderer 不直接获取 Node 能力。
2. 所有配置写入走受控服务，不允许页面自由落盘。
3. 所有敏感值在展示前必须先走脱敏。
4. 插件安装和技能安装必须绑定白名单与路径约束。
5. 日志导出前必须再次执行脱敏扫描。

## 8. 建议的开发切面

### 8.1 可直接复用

1. `electron/main` 中的 gateway 管理能力。
2. `feishu` 官方插件与安装会话能力。
3. 备份、恢复、升级、清理相关能力。
4. preload IPC 基础设施。

### 8.2 必须新增

1. 独立的产品级看门狗控制器。
2. 安装身份服务。
3. 商业化占位数据结构。
4. 输出脱敏统一策略。
5. Mclaw 自身文档体系与开发日志机制。
6. 平台兼容适配与 Windows 收口专题能力。

### 8.3 必须谨慎改造

1. 首次启动向导。
2. 飞书接入入口与默认流程。
3. 状态页对 gateway/恢复事件的展示方式。

### 8.4 Windows 优先收口清单

在新增业务功能前，以下架构切面必须完成收口：

1. 发布脚本与安装产物。
2. 环境检查与依赖修复流程。
3. gateway 进程拉起、探活、重启与失败提示。
4. 路径、日志、备份、卸载保留策略。
5. 自动更新、安装后升级与回退提示。
6. 所有用户可见的 mac-only 文案清理。

### 8.5 已识别技术债

以下文件在后续开发中应有计划地拆分重构：

| 文件 | 大小 | 问题 | 建议 |
|---|---|---|---|
| `cli.ts` | 124KB | 职责过多，承载安装、修复、环境检测等逻辑 | 拆分为 `install-service`、`env-check-service`、`repair-service` 等 |
| `openclaw-chat-service.ts` | 132KB | 单文件过大，功能域混杂 | 拆分为会话管理、消息处理、模型调度等子模块 |
| `openclaw-auth-executor.ts` | 69KB | 认证执行逻辑集中 | 拆分认证流程步骤 |
| `ipc-handlers.ts` | 48KB | IPC 处理集中注册 | 按 Desktop Service 层服务域拆分注册 |

原则：不在 Phase 1-2 做大规模重构，但每次修改时应有意识地拆分。重构时机建议在 Phase 3-4。

## 9. 架构决策

### ADR-001 基座选择

- **背景**：Mclaw 需要选择从零开始还是基于现有 Qclaw 代码库演进。
- **选项**：A. 全新仓库架构；B. 基于 Qclaw 演进。
- **决策**：选择 B，以当前 Qclaw 代码库为基础演进。
- **理由**：现有代码已具备 Electron 桌面壳、gateway 管理、飞书接入、升级恢复等大量成熟能力，重写成本过高且无必要。
- **后果**：需承担现有代码的技术债，但可通过渐进式重构解决。

### ADR-002 打包交付路线

- **背景**：dev_guide.md 明确 Docker + 可执行程序为方向，但工程实现需要确定优先级。
- **选项**：A. Docker 优先；B. 原生桌面优先，Docker 预研。
- **决策**：选择 B，v1 先完成 Windows/macOS 原生桌面版稳定交付，Docker 作为后置预研。
- **理由**：原生桌面是当前最短交付路径；Docker 在 Windows/macOS 上的安装体验、资源占用、系统权限和售后复杂度更高。
- **后果**：Docker 方案需要单独的技术验证周期，不得反向阻塞 v1 主线。

### ADR-003 渠道接入策略

- **背景**：代码中已存在飞书、钉钉、企业微信、微信等多渠道代码，需确定 v1 接入范围。
- **选项**：A. 多渠道并行接入；B. 飞书优先，其他后置。
- **决策**：选择 B，飞书官方插件（openclaw-lark）为 v1 唯一默认优先接入方案。
- **理由**：飞书是当前客户主要使用平台，官方插件稳定性更强、授权更顺、功能更完整。
- **后果**：钉钉、企微、微信代码保留但不主动维护，v2+ 再评估产品化接入。

### ADR-004 安全优先级

- **背景**：产品面向外部客户，安全边界不可协商。
- **选项**：A. 功能数量优先；B. 安全边界优先。
- **决策**：选择 B，安全限制优先级高于新增功能数量。
- **理由**：涉及敏感信息输出的变更必须先过脱敏策略。
- **后果**：可能放慢功能交付速度，但避免安全事件。

### ADR-005 Windows 优先

- **背景**：仓库已有部分 Windows 代码，但发布链路未收口，同时有大量新功能需求排队。
- **选项**：A. 继续堆新功能；B. Windows 收口优先。
- **决策**：选择 B，Windows 适配收口优先于新增功能开发。
- **理由**：在 Windows 最小可运行闭环完成前继续堆功能，会导致后续所有功能都要再做一次平台返工。
- **后果**：Phase 1-2 期间禁止新增与平台无关的大功能。
