# Mclaw PRD v1

## 1. 文档目的

本文件用于把 `dev_guide.md` 中已经确认的产品共识，沉淀为可执行的 Mclaw v1 产品需求说明。  
原则：先做可交付、可安装、可恢复、可控，再做商业化和增强能力。

## 2. 产品定义

### 2.1 产品定位

Mclaw 是基于 OpenClaw 定制的桌面客户端产品，目标用户不是内部技术人员，而是需要“下载安装即可使用”的客户。  
Mclaw 的首要目标不是提供最多功能，而是把 OpenClaw 的部署、接入、运行与恢复过程产品化。

### 2.2 产品目标

Mclaw v1 必须达成以下结果：

1. 用户可在 Windows / macOS 上完成一键安装和首次启动。
2. 用户不需要理解命令行，即可完成模型配置与飞书接入。
3. gateway 异常退出后可被监测、自动恢复，并在 UI 中有明确状态反馈。
4. 默认集成飞书官方插件能力，并提供扫码接入路径。
5. 应用在默认配置下具备基础安全边界，不泄露敏感配置。

### 2.3 非目标

以下内容不属于 v1 必须交付项：

1. 支付闭环。
2. 分销系统。
3. SaaS 化后台。
4. MemOS / Claude Code / DeerFlow 首发集成。
5. 完整的邀请码/内测码运营系统。
6. 钉钉、企业微信、微信等非飞书渠道的主动开发（代码保留但不维护）。
7. Mclaw 应用自动更新功能（推迟至 v1.5，v1 以手动下载安装主程序为主）。

### 2.4 v1 开发闸门

Mclaw v1 不是什么都能同时开工，必须按阻塞项推进：

1. `Windows 适配收口` 是 v1 第一闸门，未通过前不应继续扩展上层功能。
2. `Docker` 不是 v1 当前阶段闸门，不得反向阻塞 Windows/macOS 原生桌面交付。
3. `飞书接入`、`看门狗`、`安全脱敏` 都应建立在双平台最小运行闭环之上。

## 3. 用户角色

| 角色 | 特征 | 主要诉求 |
|---|---|---|
| 最终客户管理员 | 轻技术或非技术 | 快速安装、接入飞书、稳定运行 |
| 内部交付/售后人员 | 具备基础运维能力 | 能定位问题、能恢复、能导出必要日志 |
| 产品运营/商业化团队 | 关注授权与续费 | 需要预埋身份标识与后续可扩展接口 |

## 4. 核心问题

当前 OpenClaw / Qclaw 类产品对外交付时存在以下阻碍：

1. 安装和环境准备门槛高。
2. gateway 运行稳定性对普通用户不透明。
3. 飞书接入过程偏技术化。
4. 敏感配置与权限边界缺少产品级约束。
5. 商业化相关能力没有统一预埋点。

## 5. v1 范围

### 5.1 必做能力

| 模块 | v1 要求 | 交付标准 |
|---|---|---|
| 安装交付 | 提供 Windows / macOS 安装包 | 用户能完成安装并启动主程序 |
| OpenClaw 运行底座 | 复用现有 Qclaw/OpenClaw 管理能力，并以安装包内置 OpenClaw 本体为默认交付形态 | 首次启动在断网条件下仍可完成运行时准备与状态检测，且不把 npm 安装作为主路径 |
| OpenClaw 版本管理 | 保持 `2026.3.24` 主线基线，并提供受控升级 / 回退能力 | 当前基线可被检查、提示、备份、纠偏，为后续 `2026.4.x` 迁移做准备 |
| gateway 看门狗 | 监控、告警、自动重启、状态回传 | gateway 异常退出后能自动恢复 |
| 飞书官方插件 | 预装或首次安装即自动准备 | 用户无需手动研究插件安装命令 |
| 飞书扫码接入 | UI 提供清晰接入流程 | 用户能在客户端内看到二维码/接入流程 |
| 安全限制 | 凭证隐藏、最小权限、白名单与输出脱敏 | UI、日志、对话中不明文暴露敏感值 |
| 基础可观测性 | 提供日志查看、关键状态提示 | 能支持售后排查常见问题 |
| 内置对话能力 | 复用现有 Qclaw Chat 功能，保持可用 | 用户可在客户端内进行 AI 对话 |

补充说明：

1. “提供 Windows 安装包”不等于“electron-builder 能产出 exe”，而是要能完成真实安装、启动、运行、修复与卸载验证。
2. “复用现有 Qclaw/OpenClaw 管理能力”不等于直接继承现状，而是要完成 Windows/macOS 的一致性收口。
3. “安装即用”要求 OpenClaw 采用安装包内置本体优先，不应把在线 `npm install -g openclaw` 或 `tgz + 首启安装` 作为默认首启路径。
4. “自动更新暂不做”只指 `Mclaw` 主程序自动更新，不等于放弃 `OpenClaw` 的受控升级 / 回退能力。
5. 截至 `2026-04-09`，当前主线路径已实际收口为：
   - `win32-x64 bundled-runtime`
   - `darwin-arm64 bundled-runtime`
   - `darwin-x64 bundled-runtime`
   当前三平台已共同构成 bundled-runtime 主线；后续 `darwin-x64` 若收到新包，按 intake / candidate 分流重新验收。
6. 因此自当前时点起，v1 的下一主线应正式转入飞书接入闭环，而不是继续把 runtime 收口视作唯一前置。

### 5.2 预埋但不闭环

| 模块 | v1 处理方式 |
|---|---|
| API Key / 身份标签 | 本地生成唯一安装标识与设备身份 |
| 支付 | 只保留接口、状态位和配置位 |
| 内测码 | 保留本地校验点和服务端扩展位 |
| 分销 | 仅保留渠道来源字段 |

## 6. 关键业务流程

### 6.1 首次安装与启动

1. 用户下载安装 Mclaw。
2. 程序启动后优先启用安装包内置的 OpenClaw 本体，再执行环境与运行状态检查；安装流程只允许作为受控降级路径。
3. 若本地已有可复用 OpenClaw 状态，则提示导入或接管。
4. 若无可用状态，则进入模型配置向导。
5. 完成配置后进入飞书连接流程。
6. 接入完成后进入 Dashboard，并启动持续健康监测。

### 6.2 飞书连接流程

1. 用户在渠道页选择飞书。
2. 系统确认飞书官方插件已准备完毕。
3. 系统触发二维码或安装会话。
4. 用户在飞书 App 扫码完成绑定。
5. 系统回写连接状态，并触发一次 gateway 连通性校验。

### 6.3 异常恢复流程

1. 看门狗定期执行健康检查。
2. 发现 gateway 异常、退出或卡死后，先做轻量重试。
3. 重试失败后执行受控重启。
4. 若连续失败，则切换到“需要人工处理”状态，并暴露诊断信息。
5. 所有恢复动作写入日志，并在 UI 呈现最近一次恢复结果。

## 7. 需求明细

### 7.1 安装与交付

需求：

1. 需支持 Windows 10+ 与 macOS 11+。
2. 安装产物需尽量避免要求用户自行安装 Node、CLI 或手工配置依赖。
3. OpenClaw 需作为应用安装包内置运行底座交付，默认应直接可运行；本地安装流程与在线安装仅作为 fallback。
4. 打包形态优先围绕“桌面程序 + 本地运行底座”设计，Docker 方案作为目标架构候选，但需在技术验证后落定。
5. v1 交付必须以原生 Windows / macOS 桌面体验为准，不以 Docker Desktop 作为默认前置依赖。
6. 需区分 `Mclaw` 应用更新与 `OpenClaw` runtime 更新：v1 先保证 `OpenClaw` 受控升级 / 回退，应用自动更新后置。

验收：

1. 全新机器可完成安装。
2. 首次启动不会出现必须打开终端才能继续的阻塞步骤。
3. 在断网环境下，首次启动仍能完成 OpenClaw 运行时准备，且默认不依赖 npm 安装。
4. 当 OpenClaw 版本不在受支持窗口时，系统可给出明确升级 / 回退提示，并保留受控迁移入口。

### 7.1.1 平台交付策略

| 项目 | Windows | macOS | 当前策略 |
|---|---|---|---|
| 首发优先级 | 高 | 高 | 双平台都要交付，但 Windows 收口优先 |
| 打包方式 | NSIS 安装包 | dmg / zip | 保持原生桌面形态 |
| 默认依赖 | 不依赖 Docker Desktop | 不依赖 Docker Desktop | Docker 只做预研 |
| 运行底座 | 安装包内置 OpenClaw 载荷，首启本地安装优先 | 安装包内置 OpenClaw 载荷，首启本地安装优先 | 统一主线 |
| 发布门槛 | 必须通过最小闭环验收 | 必须通过最小闭环验收 | 任一平台不通过都不能算 v1 完成 |

### 7.2 gateway 看门狗

需求：

1. 监控对象至少包含 gateway 主进程健康状态。
2. 检测维度至少包含进程存活、健康检查结果、最近成功响应时间。
3. 支持自动重启与连续失败熔断。
4. 必须区分“正在恢复”“恢复成功”“恢复失败”三类状态。

验收：

1. 人为杀死 gateway 进程后，系统可在定义时间内发现并恢复。
2. 连续恢复失败时不会无限重启。

### 7.3 飞书官方接入

需求：

1. 飞书官方插件必须作为默认支持对象。
2. 接入路径必须在 UI 内收敛，不依赖用户自行阅读命令文档。
3. 安装、扫码、状态检查、修复动作需形成统一闭环。

渠道策略说明：

1. v1 只做飞书接入（内置 openclaw-lark 飞书官方插件）。
2. 钉钉、企业微信、微信等渠道在 v1 不做主动开发，代码保留但不主动维护。
3. 其他渠道的产品化接入推迟到 v2+。

验收：

1. 新用户按界面提示即可完成飞书接入。
2. 插件异常时可触发修复。

### 7.4 安全与权限

需求：

1. API Key、Token、App Secret 等敏感值不在普通 UI 和对话中明文展示。
2. 本地写入配置时使用现有安全写入与受控配置变更机制。
3. 插件安装、技能安装、执行工具需要白名单或受控入口。
4. 默认禁止把内部标识、密钥和路径细节直接暴露给终端用户。

验收：

1. 日志与界面默认显示脱敏值。
2. 不允许未授权插件通过产品主流程被安装。

### 7.5 商业化预埋

需求：

1. 安装实例需具备唯一身份标识。
2. 本地需预留授权状态、版本套餐、渠道来源、邀请码来源等字段。
3. 设计时需保证未来可接入服务端签发与撤销逻辑。

验收：

1. 不影响 v1 主流程。
2. 不需要二次大改即可接入服务端。

### 7.6 内置对话能力

需求：

1. v1 复用现有 Qclaw Chat 功能，保持对话能力可用。
2. 不做 Chat 架构层大规模重构，保持现有交互体验即可。
3. Chat 功能需与 gateway 状态联动，gateway 不可用时给出明确提示。

验收：

1. 用户可在客户端内发起 AI 对话并获得响应。
2. gateway 异常时 Chat 界面有状态提示。

## 8. 成功指标

| 指标 | v1 目标 |
|---|---|
| 首次安装成功率 | 可追踪，作为内测首要指标 |
| 飞书接入完成率 | 可追踪，作为渠道接入首要指标 |

## 9. 风险

| 风险 | 说明 | 应对原则 |
|---|---|---|
| Windows 适配不完整 | 已有部分 win32 逻辑，但发布、文案、验证链路仍未收口 | 先做 Windows 专项收口，再做新增功能 |
| Docker 路线复杂 | Windows/macOS 打包、权限、资源占用可能复杂 | 先做技术预研，再决定是否进入 v1 主线 |
| OpenClaw `2026.4.x` 迁移风险 | 记忆模块与 Agent 协同行为变化会影响升级、回退、备份与接管逻辑 | 先固定 `2026.3.24` 主线，再以候选线完成兼容审计 |
| 飞书扫码链路依赖外部插件行为 | 二维码获取和授权流程可能受上游变动影响 | 用受控适配层隔离外部依赖 |
| 看门狗误判 | 误把慢响应当崩溃会引发多余重启 | 引入多信号判定和熔断 |
| 商业化预埋过早侵入主线 | 主流程会被授权系统绑死 | v1 只做字段与接口预埋，不做交易闭环 |

## 10. 版本拆分

### 10.1 v1

一键安装、基础运行时管理、OpenClaw 受控版本管理、飞书扫码接入、gateway 看门狗、安全限制、日志和基础诊断。

### 10.2 v1.5

身份平台对接、授权校验、内测码/邀请码基础能力、更多看门狗监控面、`2026.4.x` 迁移、MemOS / Claude Code 接入、Docker 交付验证版。

### 10.3 v2

支付、分销、套餐管理、DeerFlow 编排层集成、更多预装技能与商业后台联动。

当前 OpenClaw 版本选择与迁移判断，统一以：

- `docs/openclaw-version-strategy.md`
- `docs/openclaw-bundled-runtime-spec.md`
- `docs/openclaw-runtime-pending-items.md`

为准。
