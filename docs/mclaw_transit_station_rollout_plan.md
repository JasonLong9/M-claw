# Mclaw 永久授权与中转站联动落地方案

更新时间：2026-05-22  
文档用途：发给产品经理，作为 `Mclaw 永久版售卖 + 授权兑换码 + 中转站充值联动` 的产品与研发落地方案。  
适用场景：用户在抖音购买 `Mclaw` 软件包，获得一个软件授权兑换码；软件永久可用，模型能力、余额与充值全部来自自有中转站。

---

## 1. 方案一句话

`Mclaw` 卖的是“客户端永久使用权”，不是“模型无限使用权”。

用户购买后：

1. 下载 `Mclaw`
2. 登录账号
3. 输入软件授权兑换码
4. 开通 `Mclaw 永久版`
5. 后续模型使用时，余额不足则在 `Mclaw` 内跳转到中转站充值

所以整个系统分成两层：

- `Mclaw 客户端`：桌面入口，负责登录、兑换、显示余额、发起模型请求
- `中转站后端`：统一账号中心 + 永久授权 + 钱包余额 + 模型消费 + 充值系统

---

## 2. 产品目标

## 2.1 核心目标

面向小白用户，把“买软件”和“用模型”拆开，但对用户的理解负担尽可能低：

- 买一次软件：永久使用 `Mclaw`
- 用模型：按余额消耗
- 没余额：去充值

## 2.2 产品原则

1. `Mclaw 永久授权` 与 `中转站余额` 分开
2. 软件授权兑换码只负责开通软件，不负责充值
3. 用户账号统一，客户端和中转站共用一套账号
4. 前台不向用户暴露技术术语，例如 `API Key`、`Provider`、`License ID`
5. 流程要尽量傻瓜化：买完后 3 分钟内可以开始用

## 3. 商业模式定义

## 3.1 售卖内容

抖音售卖的是：

- `Mclaw 永久版`
- 可选：`Mclaw 永久版 + 赠送体验余额`
- 可选：`Mclaw 永久版 Pro（更多设备上限）`

## 3.2 用户买到的是什么

用户买到的是：

- `Mclaw` 客户端永久使用权
- 一个软件授权兑换码
- 可选赠送少量体验余额

## 3.3 用户后续消费什么

用户后续不再购买软件授权，而是购买：

- 中转站余额充值
- 模型套餐
- 企业额度包

注意：

- 永久的是软件
- 收费的是模型调用能力

---

## 4. 为什么授权后端要放在中转站

不建议单独做一套 `Mclaw 授权后端`。

推荐方案：

- 在现有中转站后端里增加 `Mclaw 授权模块`

原因：

1. 账号统一：避免客户端和中转站两套用户
2. 钱包统一：余额、订单、消费天然关联
3. 售后统一：客服一次就能查授权、设备、余额、订单
4. 安全统一：授权校验必须服务端完成，不能放客户端本地

## 5. 用户旅程设计

## 5.1 首购用户旅程

### 步骤 1：抖音购买

用户在抖音购买 `Mclaw 永久版`。

### 步骤 2：收到发货信息

发货内容：

1. 下载地址
2. 软件授权兑换码
3. 三步说明

### 步骤 3：下载并安装 Mclaw

用户安装桌面客户端。

### 步骤 4：登录 / 注册

用户首次打开，先登录或注册统一账号。

### 步骤 5：输入授权兑换码

用户在 `Mclaw` 内输入兑换码，开通永久版。

### 步骤 6：开始使用

授权成功后，进入主界面，显示：

- 永久版已开通
- 当前余额
- 去充值按钮

## 5.2 老用户旅程

老用户以后主要做两件事：

1. 继续用软件
2. 余额不足时去充值

也就是说：

- 永久版解决“能否用客户端”
- 余额解决“能否继续调用模型”

## 6. 用户界面设计（Mclaw）

## 6.1 首次启动页

只保留两个核心动作：

- 登录 / 注册
- 输入兑换码

推荐文案：

- `登录后输入兑换码，开通 Mclaw 永久版`

## 6.2 授权成功页

推荐展示：

- `Mclaw 永久版已开通`
- `可绑定设备数：2 台`
- `赠送余额：xx 元`（如有）

主按钮：

- `立即开始`

## 6.3 用户中心页

固定展示：

- `Mclaw 永久版：已开通`
- `当前余额：xx 元`
- `当前可用模型：xx 个`
- `设备绑定数：1/2`
- `去充值`

## 6.4 余额不足提示

提示必须把“软件授权”和“模型余额”区分清楚：

正确示例：

- `Mclaw 永久版：已开通`

错误示例：

- `授权失效`
- `系统不可用`

因为软件并没有失效，只是余额不足。

## 7. 授权兑换码设计

## 7.1 设计目标

授权兑换码需要解决 5 个问题：

1. 防伪造
2. 防重复使用
3. 能绑定到某个用户账号
4. 能追踪来源订单
5. 能支持客服售后查询

## 7.2 兑换码职责

软件授权兑换码只负责：

- 开通 `Mclaw 永久版`

不负责：

- 给中转站充值
- 发模型套餐

## 7.3 推荐码格式

建议采用高可读格式：

`MCLAW-8F4K-Q2MN-7PXD`

规则建议：

- 16~20 位有效字符
- 4 段分隔
- 大写字母 + 数字
- 避免 `O/0`、`I/1`

## 7.4 状态流转

兑换码状态建议：

- `unused`：未使用
- `redeemed`：已使用
- `disabled`：已禁用
- `expired`：已过期

## 7.5 如何判断兑换码是否正确、可用、已被使用

这个判断必须由中转站后端完成，不能由 `Mclaw` 本地判断。

后端校验顺序：

1. 码格式是否基本合法
2. 数据库中是否存在该码
3. `status` 是否为 `unused`
4. 是否已过期
5. 是否已经被兑换
6. 当前用户是否已经拥有永久版
7. 如果全部通过，则发放永久授权

也就是说：

- `Mclaw` 不负责判断真假
- `Mclaw` 只负责把码提交给后端
- 最终结果由中转站后端返回

## 7.6 并发防重复兑换

必须考虑两个人同时拿同一个码去兑换的情况。

后端必须用数据库事务或原子更新保证：

- 同一个码只能成功兑换一次

典型做法：

- 更新兑换码状态时附带条件 `status = unused`
- 只有一条请求能更新成功

1. `auth`

## 10. API 设计

## 10.1 授权相关

### 1. 兑换软件授权码

`POST /api/mclaw/license/redeem`

请求：

```json
{
  "code": "MCLAW-8F4K-Q2MN-7PXD",
  "device_fingerprint": "dev_xxx",
  "device_name": "James-PC"
}
```

成功返回：

```json
{
  "ok": true,
  "license": {
    "type": "permanent",
    "status": "active",
    "deviceLimit": 2
  },
  "gift": {
    "walletCredit": 20
  }
}
```

失败返回示例：

```json
{
  "ok": false,
  "errorCode": "CODE_ALREADY_USED",
  "message": "兑换码已被使用"
}
```

### 2. 获取当前授权状态

`GET /api/mclaw/license/me`

返回：

```json
{
  "licensed": true,
  "licenseType": "permanent",
  "status": "active",
  "deviceLimit": 2,
  "boundDevices": 1
}
```

### 3. 绑定设备

`POST /api/mclaw/license/device/bind`

### 4. 解绑设备

`POST /api/mclaw/license/device/unbind`

### 5. 获取设备列表

`GET /api/mclaw/license/device/list`

## 10.2 钱包相关

### 1. 获取余额

`GET /api/wallet/me`

### 2. 获取流水

`GET /api/wallet/transactions`

## 10.3 模型相关

### 1. 获取可用模型

`GET /api/models/available`

返回：

- 当前账号可用哪些模型
- 各模型是否可用
- 是否因为余额不足而受限

## 10.4 充值跳转

### 1. 获取充值页地址

`GET /api/wallet/recharge-url`

返回：

```json
{
  "url": "https://your-transit-site.com/recharge?from=mclaw"
}
```

## 14. 风控与售后

## 14.1 最低限度风控

必须做：

1. 兑换码只能使用一次
2. 一个账号第一版只允许拥有一个永久授权
3. 设备数超限时，禁止新设备绑定
4. 后台支持人工禁用授权
5. 后台支持人工解绑设备

## 14.2 客服最少查询能力

客服必须能按以下维度查询：

- 订单号
- 兑换码
- 用户账号
- 永久授权状态
- 设备绑定记录
- 钱包余额

## 14.3 常见售后场景

### 场景 1：用户换电脑

做法：

- 用户在自助页解绑旧设备
- 或客服后台手动解绑

### 场景 2：兑换码被盗用

做法：

- 后台禁用对应授权
- 重新发放新码

### 场景 3：用户不会使用

做法：

- 发固定三步说明
- 下载页 + 登录 + 兑换页指引

## 17. 产品经理待确认项

以下问题需要产品经理明确：

1. `Mclaw 永久版` 是否附赠体验余额？附赠多少？
2. 普通版和 Pro 版是否同时上线？
3. 普通版默认可绑定几台设备？建议 `2 台`
4. 是否允许用户自助解绑设备？每月是否限次数？
5. 是否允许一个账号重复兑换永久版？第一版建议 `不允许`
6. 充值页是否必须从 `Mclaw` 内打开内嵌页，还是浏览器跳转即可？
7. 抖音首发是否只卖一个 SKU？建议第一版只卖 `Mclaw 永久版`
8. 是否需要客服后台在首版同步上线？

## 18. 最终建议

最终建议只有一句话：

**把 `Mclaw 永久授权` 作为中转站后端里的一个授权模块来做，兑换码只负责开通软件，余额充值全部走中转站网页。**

这样做的优势：

- 用户理解简单
- 系统职责清晰
- 研发边界明确
- 售后查询方便
- 后续扩展成本低

---

## 19. 一页总结

### 用户看到的

- 买一次 `Mclaw 永久版`
- 输入兑换码开通
- 永久使用客户端
- 模型按余额使用
- 余额不足去充值

### 系统里实际做的

- 中转站后端增加永久授权模块
- 统一账号
- 软件授权兑换码
- 永久授权记录
- 设备绑定
- 钱包余额与模型消费继续复用中转站现有能力

### 第一版不要做的

- 单独授权后端
- 充值兑换码
- 多层分销
- 复杂授权层级

### 第一版最重要的

- 一单一码
- 输入即开通
- 永久版状态清晰
- 余额清晰展示
- 一键跳转充值
