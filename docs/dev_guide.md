Mclaw 定制产品讨论总览
产品定位
Mclaw 是基于 OpenClaw 定制的自有产品，目标是交付给客户使用，而不是只给内部技术人员使用。产品形态偏向桌面 / 本地安装程序，强调 Windows / Mac 双平台一键安装、打开即用。

补充约束：

1. 任何“OpenClaw 内置本体”设计都必须默认同时考虑 `Windows` 与 `macOS`，不能只写成单平台实验方案。
2. 若某一阶段先落某个平台代码，也必须同步给出另一个平台的目录结构、元数据约定、验收闸门和后续接入位。
3. 除非文档明确标注“临时过渡实现”，否则不得把单平台实现写成最终交付方案。
核心价值：
- 降低部署门槛
- 保证长期稳定在线
- 强化飞书原生接入体验
- 做好安全与权限边界
- 为后续商业化预埋能力
已明确的核心需求
1. 简易安装版
- Windows / Mac 下载安装即用
- 尽量跳过环境安装、依赖配置、手工部署
- OpenClaw 运行底座应随安装包内置，目标是安装包直接携带可运行的 OpenClaw 本体，而不是只内置安装流程
- `tgz + 首启安装` 只能作为阶段性过渡方案，不能作为 v1 最终交付定义
- 当前生效的 v1 默认交付路线是：`桌面壳 + 平台专属内置 OpenClaw 本地服务本体`
- 因此 v1 的发布目标是：
  - 一个 Windows 安装包
  - 一个 macOS 安装包
- `Docker + 桌面程序` 只保留为 `Phase 10 / v1.5-v2` 预研方向，不再作为当前主线默认实现
2. 看门狗机制
- 实时监控 gateway
- 防止 gateway 死机、崩溃、闪退
- 异常时自动修复、自动重启
- 目标是 7x24 在线，用户无感恢复
3. 飞书官方插件预装
- 明确要内置 openclaw-lark
- 原因是群里当前机器人能力本身就依赖它
- 这被视为后续所有飞书能力扩展的基础中的基础
4. 首次扫码接入飞书
- 希望客户打开程序后，有简单按钮或默认流程
- 直接弹飞书二维码，用户扫码即可完成连接
- 技术上可行，但仍需用户在飞书 App 内扫码
5. 支付与商业化
- 使用支付宝支付
- 已有企业支付宝主体
- 需要预埋 1000 个内测码
- 后续需要考虑分销逻辑
6. API Key / 身份标签
- 每个客户安装的 App 默认生成一个 Key
- 未来对接自建的 coding plan / API key 管理平台
- 当前可先做本地生成 + 本地存储的第一阶段
7. 安全限制
- 不能在对话里吐出内部敏感信息，如 API Key、Token、ID
- 需要从 Tool Policy、Prompt、权限隔离、文件访问限制多层一起做
8. 技能化能力
- 把 360 安全指南内化成预装 skill
- 把 DeepWiki 之类的项目解读能力也考虑 skill 化
技术方向共识
打包路线
- v1 主线采用 `桌面壳 + 平台专属内置 OpenClaw 本体`
- 目的不是云端 SaaS，而是本地可交付、可安装、可控
- Docker 保留为后置专题，用于评估更强隔离、运维一致性或未来增强版交付
看门狗路线
- 不只是状态展示，而是真正的进程守护和异常恢复
- 这是 Mclaw 区别于普通 OpenClaw 使用方式的关键能力
飞书接入路线
- 预装 openclaw-lark
- 首次启动触发绑定流程，OpenClaw 本体应已由安装包直接提供，不能把“现场安装 OpenClaw”当成默认主路径
- 将终端二维码渲染进 UI，形成“连接飞书”按钮式体验
AI 开发路线
- 代码相关工作通过 exec 启动 Claude Code，并接入 coding plan
- 倾向于由“总设计师”协调多个 AI 助手并行开发
能力底座路线
- 预装 / 接入飞书官方插件
- 预装安全加固 skill
- 讨论过接入 MemOS / MambaOS 记忆系统
- 讨论过把 DeerFlow 作为调度大脑或编排层
飞书官方插件共识
- 官方插件优先于社区插件
- 选择理由：稳定性更强、授权流程更顺、功能更完整、安全防护更成熟、更新更快、有官方支持
- 目标体验：程序里直接有飞书连接入口，扫码即可完成绑定，后续通过飞书机器人 / 群聊交互或远控
安全机制共识
- 明确要求把“360 安全龙虾指南”内化成 skill，并预制到 Mclaw 里
- 已提炼出的安全重点包括：
  - 默认端口不能暴露公网
  - API Key / Token 不能明文存储或泄露
  - Shell / Exec 工具要最小权限
  - 防提示词注入
  - 防记忆投毒
  - 第三方插件白名单
  - 多智能体行为监控
Qclaw 对比意义
Qclaw 被当作参考对象，而不是终局方案。
已讨论出的判断：
- Qclaw 已具备一些基础安全能力，如 preload 隔离、原子写入、进程隔离
- 但它在你们最看重的几个点上不够强：
  - 没有明显的看门狗 / 自动恢复
  - 缺少明确的卡顿熔断 / 超时控制
  - 缺少“安全加固 + 稳定在线 + 商业化”整套方案
因此，Mclaw 的差异化机会非常明确：不是重复做一个桌面壳，而是补强 Qclaw 的短板。
已确定事项
- Mclaw 是基于 OpenClaw 的定制产品
- 产品核心形态是一键安装的桌面 / 本地程序
- v1 的“内置 OpenClaw”定义为内置可运行本体，不是只内置 `tgz` 或在线/离线安装流程
- 必须做看门狗与自动修复
- 必须内置飞书官方插件
- 必须支持扫码连接飞书
- 必须做安全限制，不能泄露敏感配置
- 要预留支付、内测码、分销、API Key 平台对接能力
- 要把 360 安全方案 skill 化并预装
仍待细化确认的事项
- 打包架构：当前 v1 已收敛为 `桌面壳 + 内置本地服务本体`；待确认的是后续是否需要在 v1.5/v2 引入 Docker 交付支线
- 看门狗粒度：只监控 gateway，还是同时监控模型通道、插件状态、远控链路
- API Key 生命周期：本地生成、服务端签发、是否支持撤销 / 重置 / 续费绑定
- 支付逻辑：一次性买断、订阅制，还是点数 / 配额制
- 飞书连接体验：首次启动自动弹码，还是用户手动点“连接飞书”
- DeerFlow / MemOS 是首发集成，还是后续增强版
建议推进顺序
1. 先冻结 Mclaw v1 的最小可交付范围：一键安装、看门狗、飞书扫码接入、安全限制
2. 紧接着先完成 `Phase 2` 的真实 OpenClaw 内置本体获取、入库和双平台断网验证，再进入新的功能主线
3. 再定义 v1.5 / v2：支付、分销、邀请码、记忆系统、DeerFlow 编排
4. 用 Qclaw 做代码复用源，但产品目标不要被它限制
5. 单独形成 Mclaw PRD、技术架构草案、功能边界表

当前补充结论：

1. “内置 OpenClaw 本体”当前最大的风险不在分发逻辑，而在真实 runtime 载荷获取。
2. 已实测确认：仅解包 `openclaw-*.tgz` 不能作为 bundled runtime 入库。
3. 后续任何 runtime 入仓，必须先满足：
   - 来源明确
   - 版本明确
   - 依赖闭包明确
   - 目标平台明确
   - `--version` 直探测通过
4. 对应执行规范见：
   - `docs/openclaw-bundled-runtime-acquisition-sop.md`
