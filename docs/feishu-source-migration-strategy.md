# 飞书旧配置来源修复策略

这份文档用于说明：

1. 为什么有些飞书 Bot 会显示 `来源：待确认`
2. 我们为什么暂时不做激进自动迁移
3. 后续如何安全地补齐旧配置来源

## 1. 背景

当前新版本的 `Mclaw` 已经会在飞书 Bot 配置里记录来源字段：

- `created`：来自 `新建机器人`
- `linked`：来自 `关联已有机器人`

但历史上更早的飞书配置并没有记录这个字段，所以旧配置加载进来后，会显示：

- `来源：待确认`

这不是配置损坏，而是历史信息缺失。

## 2. 为什么不能直接自动猜

从现有旧配置里，我们通常还能看到：

- `App ID`
- `App Secret`
- `accountId`
- `agentId`
- `name`

但这些字段本身并不能稳定证明它最初来自哪条接入路径。

例如：

1. 一个旧 Bot 可能是早期“新建机器人”跑出来的
2. 也可能是手动“关联已有机器人”后写进去的
3. 最终落到配置里的结构却可能非常接近

所以如果直接自动猜来源，就容易把：

- 本来是 `created`
- 错标成 `linked`

或者反过来。

这会比保留 `unknown` 更危险，因为会污染后续联调结论。

## 3. 当前策略

当前采用的是保守策略：

1. 新接入的飞书 Bot
   - 在接入时直接写入来源
2. 旧配置里的飞书 Bot
   - 若没有来源字段，则继续保留为 `unknown`
   - 控制面板显示 `来源：待确认`
   - 同时给出提示：这通常是旧配置或较早版本遗留

这套策略的目标是：

- 先保证新数据可追溯
- 不误伤旧数据

## 4. 什么时候可以补来源

只有在你能拿到额外证据时，才建议补旧配置来源，例如：

1. 你明确知道这个 Bot 是这轮刚通过 `新建机器人` 路径创建的
2. 你明确知道这个 Bot 是从已有飞书应用手动绑定进来的
3. 你有历史联调记录、聊天记录或操作录像可交叉验证

如果没有这些额外证据，建议继续保留为 `来源：待确认`。

## 5. 后续可选方案

后续如果要继续推进来源修复，可以考虑两种安全方案。

### 方案 A：人工确认后写回

由联调人员在确认来源后，手动把旧 Bot 标记成：

- `created`
- 或 `linked`

优点：

- 最安全
- 不误判

缺点：

- 需要人工参与

### 方案 B：只对高置信度场景做半自动修复

只有在满足一组严格条件时才自动补：

- 有明确的新建安装器日志
- 有本轮操作记录
- 有对应的 Bot 新增时间或事件证据

优点：

- 比全人工省力

缺点：

- 仍需要设计高置信度规则
- 当前项目阶段暂时不值得优先投入

## 6. 当前结论

在现阶段，最稳做法是：

1. 新接入的 Bot 直接记录来源
2. 旧配置继续显示 `来源：待确认`
3. 真实联调时，用现场记录表补充上下文
